# Member profiles, group-vs-group matches, seeding, and crit‑9 real‑time

## Context

Right now `results.winner`/`results.loser` are free text — you can log "1 beat
2" in a group where no one named 1 or 2 exists. There's also no concept of a
profile picture, no way to record a match between two *groups* (only between
two members of the same group), and no seed data to click through any of this
by hand. Separately, crit 9 (due **Mon 12 Oct, 13:30**, ~2 days out) requires
the app to be real-time — a change one person makes has to show up for
everyone else within about a second, no reload — plus one written-down
decision about concurrent use. None of the current code does that yet.

This plan builds all four together because they interact: once logging a
result requires picking a real member, a member who just joined has to show
up in other people's open forms *live*, or the membership gate itself becomes
the thing fighting the app's "logging should be effortless" goal
(`README.md`). That interaction is also where the crit-9 concurrency decision
comes from, rather than being bolted on separately.

Decisions already made with you: avatars are generated by default and
uploadable (like Reddit's default avatar + custom picture), group-vs-group
matches are a single final score per match (not per-player rows), and crit
9's real-time requirement is in scope here.

## Schema changes (`src/db.ts`)

- `members`: add `avatar_blob BLOB`, `avatar_mime TEXT`, `avatar_updated_at TEXT`
  (all nullable — `NULL` means "use the generated avatar"), via the same
  `ALTER TABLE ... ADD COLUMN` migration pattern already used for
  `password_hash`.
- `groups`: add the same three `avatar_*` columns, for the group's own
  profile picture.
- `results`: add nullable `winner_member_id`, `loser_member_id` (FK to
  `members`). Keep the existing `winner`/`loser` text columns (populated from
  the member's name at logging time) so old rows and existing display code
  keep working untouched; new rows get both.
- New table `group_matches`: `id`, `group_a_id`, `group_b_id`, `game`,
  `score_a`, `score_b`, `logged_by_member_id`, `created_at`. One row per
  inter-group match, visible on both groups' pages via
  `WHERE group_a_id = ? OR group_b_id = ?`.

## 1. Members must be real, and can't beat themselves

- `src/pages.ts`: replace the free-text `winner`/`loser` inputs in the log-a-result
  form with `<select>`s populated from `resultsForGroup`'s sibling,
  `membersForGroup(group.id)` (new query in `db.ts`), using member id as the
  option value.
- `src/server.ts` (`POST /g/:code/results`): resolve `winner`/`loser` as
  member ids, require both to belong to this group, and reject
  `winner === loser`. On failure, re-render the group page with an error
  (same pattern `authError` already uses) and don't insert a row.
- `src/db.ts` `addResult`: take member ids, look up names, store both id and
  name columns.
- **Existing test fix**: `spec/scorekeeping.test.ts` logs results against
  `"Sam"`, `"Ghost"`, `"Robin"` without registering them — once membership is
  enforced these would now be rejected. Register every named player before
  logging in that file (the stale-token case doesn't need a real `loser`,
  since it must fail before membership is even checked).

## 2. Avatars (members and groups)

- New `src/avatars.ts`:
  - `generatedAvatar(seed: string): string` — a deterministic SVG (initials +
    a color picked from a small fixed palette by hashing `seed`). No upload,
    no dependency, no storage.
  - Shared helpers for reading/validating an uploaded file: accept
    `image/png`, `image/jpeg`, `image/webp`; reject anything else or over
    300KB (no resizing library — keeps the no-native-deps approach
    `PROCESS.md` already committed to; a hard cap instead).
- Add `@fastify/multipart` (the only new dependency) and register it in
  `src/server.ts`.
- Routes, both following the same shape:
  - `GET /g/:code/members/:id/avatar` and `GET /g/:code/avatar` — serve the
    stored blob with its mime type if set, otherwise `generatedAvatar(...)`
    as `image/svg+xml`. `Cache-Control`/`ETag` from `avatar_updated_at`.
  - `POST /g/:code/members/:id/avatar` — only the signed-in member themself
    (`currentMember(req, group).id === id`); `POST /g/:code/avatar` — any
    signed-in member of the group (there's no group-admin concept, consistent
    with the existing trust model).
- `src/pages.ts`: show the avatar (`<img>` pointing at the routes above) next
  to each result row, on the sign-in/register card header, and in the group
  page header (the group's own "profile picture"), with a small upload
  control wherever a signed-in member can change one.

## 3. Group-vs-group matches

- `src/db.ts`: `addGroupMatch`, `groupMatchesForGroup(groupId)` (joins both
  group names/codes for display).
- `src/server.ts`: `POST /g/:code/matches` — signed-in member of this group
  enters an opponent group code + game + both scores; 404/error if the code
  doesn't resolve to a group.
- `src/pages.ts`: a "Group matches" section on the group page, separate from
  the intra-group results list, showing the opponent group's name + avatar +
  score, with the log-a-match form visible to signed-in members. Appears
  identically on both groups' pages since it's the same row.

## 4. Real-time (crit 9) + the concurrency decision

- New `src/live.ts`: a tiny in-memory pub-sub — `subscribe(code, fn)` /
  `broadcast(code, event)` — scoped per group code. In-memory is enough
  because `fly.toml` runs exactly one machine (`min_machines_running = 0`,
  no horizontal scaling), so there's only ever one process to broadcast
  from.
- `GET /g/:code/events` — an SSE endpoint (`reply.hijack()` + raw writes to
  `reply.raw`, no new dependency). On connect, subscribe; on `req.raw`
  `close`, unsubscribe.
- Broadcast points, each sending a re-rendered HTML fragment the client swaps
  in directly (reusing the same render functions as the full page, so there's
  one template, not two):
  - after `addResult` → a `result` event with the refreshed results list
  - after `addGroupMatch` → a `group-match` event with the refreshed group
    matches list
  - after `registerMember` → a `member` event with the refreshed `<option>`
    list for the winner/loser selects
- `src/pages.ts`: wrap the results list, group-matches list, and the two
  `<select>`s in elements with stable ids; a small inline `<script>` opens
  `new EventSource('/g/:code/events')` and replaces the matching element's
  `innerHTML` per event type.
- **The decision, written down** in `decisions/0001-live-update-scope.md`
  (ADR form, as the brief suggests): *new results, new group matches, and new
  member sign-ups push live to everyone with the group open; avatar changes
  do not* — a viewer sees a stale picture until their next reload. Options
  considered: push everything (rejected — image bytes are comparatively
  rare-churn and heavy for a 256MB machine to fan out); push only results,
  the minimum crit-9 asks for (rejected — once logging requires picking a
  real member, a person who just joined would be invisible in everyone
  else's open dropdown until they reload, which directly fights the
  "logging should be effortless" goal in `README.md`). Reconnecting (a
  closed tab, or the next day) just does a normal page load, which is
  already fully up to date from SQLite — no separate reconnect logic needed.

## 5. Seed script

- `scripts/seed.ts`, using the real `db.ts` functions (not raw SQL) so it
  exercises the actual code paths: creates 3 groups, 3–4 members each with
  known passwords, a handful of intra-group results, and 2 group-vs-group
  matches between the seeded groups. Skips groups that already exist by name
  instead of duplicating on a second run. Prints a summary (codes + logins)
  so you can click through by hand afterwards.
- `package.json`: `"seed": "DB_PATH=./data/dev.db node scripts/seed.ts"` —
  same `DB_PATH` convention as `dev`, so it never touches the production
  volume unless `DB_PATH` is explicitly overridden.

## 6. Spec tests ("test all the features too")

All run the existing way — real HTTP against the running app
(`spec/global-setup.ts`), asserting the contract, not the implementation:

- `spec/scorekeeping.test.ts`: fix the two now-invalid existing cases (above),
  add "logging a result naming someone who isn't a member is rejected" and
  "winner and loser can't be the same member."
- `spec/avatars.test.ts`: fresh member serves a generated (`image/svg+xml`)
  avatar; uploading a valid small PNG switches it to `image/png` with
  matching bytes; an oversized/invalid upload is rejected and the avatar is
  unchanged; same two cases for a group avatar.
- `spec/group-matches.test.ts`: a match between two seeded/created groups
  appears on both groups' pages with the right score; an unknown opponent
  code is rejected.
- `spec/live-updates.test.ts`: open the SSE stream for a group, log a result
  from a second request, assert the stream emits a matching event within a
  couple of seconds; same for a new member showing up in the stream.

## Verification

1. `pnpm typecheck`
2. Start the app (`pnpm dev` or equivalent) and run `pnpm seed`, then `pnpm check` —
   all spec files green, including the new ones.
3. By hand: open a seeded group's page in two browser windows, log a result
   in one, watch it appear in the other without reloading; try logging a
   result for a made-up name and confirm it's refused; upload an avatar and
   confirm it replaces the generated one; log a group-vs-group match and
   confirm it shows on both groups' pages.
4. `flyctl deploy --remote-only --ha=false -a comp4020-final-raazseven`, then
   repeat step 3 against the live URL (crit 9's bar is deployed, not just
   local).
5. Commit incrementally through the phases above (schema → avatars → group
   matches → real-time/ADR → seed/tests), not as one giant commit — that
   commit history is the process evidence `PROCESS.md` and
   `reflections/crit-9.md` cite.

## Addendum 1: fully responsive, then a real home page + logo

Two follow-up rounds after the plan above shipped, both directed live rather
than re-planned from scratch:

- **Responsive pass.** The group page was pinned to a ~40rem column at every
  screen width. Added one `--page-width` variable driving header/main/footer
  together (40rem → 48rem at 700px → 72rem at 1024px) and a real two-column
  `.group-layout` grid at ≥900px (actions left, results/group-matches feed
  right), instead of one column stretched wide. Found and fixed a real bug
  along the way: `.avatar-upload` is a `<form>`, and the generic `form` rule
  sets `flex-direction: column` — `.avatar-upload` only overrode
  `display`/`align-items`/`gap`, so the column direction leaked through and
  centred the file input above the button instead of beside it.
- **Logo + real home page.** The home page was two bare form cards under one
  tagline. Added `logoMark()` (a small SVG badge, reused as the favicon),
  and rebuilt the home page around patterns from actual competitor apps
  (Inscore, Point Wars, Versus) plus current SaaS landing-page structure: a
  nav with Log in / Sign up, an outcome-focused hero, a 3-step "how it
  works," a feature grid, then the real action cards. The accounts here are
  per-group, not global, so "Log in"/"Sign up" are real anchors to the
  actual two flows (create a group / enter a code), not a fake global-auth
  UI layered on top of an architecture that doesn't have one.
- **Design pass.** A secondary icon-only palette, the Sora display typeface,
  a small hand-drawn icon set for the steps/features, restrained motion
  (gated behind `prefers-reduced-motion`), and a crafted hero visual — a
  product-preview mockup built from the same CSS tokens as the real app,
  not a stock photo or a screenshot that would go stale the next time the
  UI changes. Found and fixed two more real bugs surfaced by the narrower
  sidebar column: `.cards-row`'s `1fr 1fr` track had no 0-floor and blew out
  past its container once the sidebar made room genuinely tight (fixed with
  `minmax(0, 1fr)`, plus always-stack in that specific sidebar context); and
  `<input>` is `inline-block` by default and was only ever full-width by the
  coincidence of being a direct flex child of `<form>` (fixed with an
  explicit `width: 100%`).

## Addendum 2: a group needs a whole profile to exist, not just a name

A group used to need only a name. Creating one now requires a bio, at least
one game tag, and a photo too — all mandatory, all server-validated, not
just HTML `required` attributes — so a group has something real on its page
before anyone's logged a result, for the same reason crit 8 required a
member account instead of a bare name. `POST /groups` moved from formbody to
multipart (the photo travels in the same request); a failed submission
re-fills the name/bio/tags but not the photo, which HTML has no way to hand
back to a form. Every spec file's own copy of `createGroup()` only ever sent
a name, so this also meant consolidating the five near-identical copies into
one `spec/support.ts` rather than patching each to build a valid multipart
profile separately.

Being asked directly "did you test every feature" was worth doing honestly
rather than asserting yes: three real gaps turned up that predate this
addendum (the group-match live SSE event was never asserted, only the
rendered page after the fact; the tied-score "drew with" outcome branch was
never exercised; registering a duplicate name and logging in with the wrong
password were both enforced in `src/db.ts` but never asserted by a spec
test) and are closed now rather than left for later. `pnpm check`: 25/25.

## Addendum 3: three corrections to the group-profile feature

The mandatory photo, the free-text "tags," and the home-page card were each
revisited once actually used, in that order:

- The mandatory photo was dropped in favour of a choice ("generate one for
  me" / "upload a photo") — it had broken the generated-by-default pattern
  members already had, for no reason the brief asked for.
- "Tags" became a real `tags`/`group_tags` schema (~39 curated entries
  across video games / real-world sports / board & card games, picked via
  checkbox chips, plus a free-text field that creates a real row rather than
  a second storage mechanism) instead of a comma-separated text box.
- The whole form moved off the home page to its own `/new` route once it was
  clear a name/bio/tag-picker/photo form squeezed into half a two-column row
  next to a one-field "log in" card was never going to look balanced no
  matter how the CSS was tuned — the mismatch was the symptom, not the bug.

A later direct question — "check if all the crit 9 requirements are met" —
caught this file and `PROCESS.md` both falling behind these three commits.
Re-verified rather than assumed at that point: `pnpm check` 30/30, and the
SSE real-time check re-run against the *current* live deploy (not the one
checked earlier in the week), confirming a result still arrives on a second
open session within about two seconds through Fly's actual proxy.

## Addendum 4: accounts go global, with roles

The account model above (and in crit 8) was per-group on purpose — `README.md`
called it out as deliberate. Walked through from each user's perspective
instead, it didn't hold up: logging in asked for a group code before the
site would say who you were, nothing showed you were signed in outside one
group's card, there was no way to be one person in two groups, and every
signed-in member of a group could do anything any other member could,
including the group's creator having no more standing than someone who
joined a minute ago.

This addendum reverses that decision. Full reasoning, options considered,
and migration approach are in `decisions/0002-global-accounts.md`; the short
version:

- **`users`** (globally unique name, one password, one photo) replaces
  per-group member identity; **`memberships`** (`user_id`, `group_id`,
  `role`) is the join table recording who's in which group and as what.
  `role` is `'owner'` (the group's creator) or `'member'`.
- One global `session` cookie (`path: "/"`) replaces the per-group
  `member_${code}` cookie. `/signup` and `/login` work with no group code;
  `/me` is a dashboard listing every group you're in and your role in each;
  creating or joining a group now requires being signed in first.
- Owner-only, gated by a `requireOwner` check (403 for anyone else): editing
  a group's profile, removing a member. Everything a member could already do
  (log a result, log a group match) stays open to any member — this is an
  added gate, not a general lockdown.
- The old `members` table is kept, untouched, as the one-time migration
  source — never dropped, same rule as every earlier migration this project
  has done. Every existing membership becomes its **own** new account on
  first startup (never merged by name across groups, which would otherwise
  silently hand one person's identity to an unrelated namesake in another
  group); a name collision during migration gets a numeric suffix.
- `group_matches.logged_by_member_id` was `NOT NULL`, which SQLite can't
  relax with a plain `ALTER TABLE ADD COLUMN` — that one table went through
  a rename → recreate → copy → drop rebuild instead, the first time this
  project needed that heavier migration shape.

Three scoped questions were answered before this was planned in detail:
exactly what "owner" gates (profile edit + member removal, not everything),
what happens to a membership across the per-group → global-name change
(each becomes its own separate account, not merged), and whether
create/join requires login first (yes, landing on a dashboard). All three
answers are recorded, with the "why," in the ADR rather than just acted on
silently.

Two bugs caught before shipping, both from checking existing test
expectations rather than assuming the new routes matched the old ones
exactly: splitting one combined register-and-join step into a separate
global signup plus a `/g/:code/join` call dropped the live `member` SSE
broadcast the old route used to fire; and `/signup`/`/login`/`/g/:code/profile`
were initially built with the same manual multipart parsing the photo-upload
routes need, despite having no file field, and were switched to the plain
`formbody` plugin instead.

Making names globally unique also broke several spec files that had reused
the same literal names ("Priya," "Sam") across files back when each group
was its own namespace — this showed up first as a pile of `Error: Test
timed out in 5000ms` failures under the suite's normal parallel execution,
which looked like a server regression but wasn't. Running the most
suspicious file alone (no timeouts, two plain assertion failures) separated
the real naming-collision bug from parallelism noise; fixing the collision
in `spec/support.ts` and re-running with `--no-file-parallelism` reduced the
whole suite to exactly one real remaining bug (a test re-logging-in with a
literal name that `register()` no longer actually registers verbatim),
fixed directly. `vitest.config.ts` now runs spec files one at a time —
every spec file shares one real dev server and one SQLite file by design,
and vitest's default per-file parallelism isn't a fit for that. `pnpm check`
is 39/39 clean.
