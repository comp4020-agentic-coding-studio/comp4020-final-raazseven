# Member profiles, group-vs-group matches, seeding, and crit‑9 real‑time

## Context

Right now `results.winner`/`results.loser` are free text — you can log "1 beat
2" in a group where no one named 1 or 2 exists. There's also no concept of a
profile picture, no way to record a match between two *groups* (only between
two members of the same group), and no seed data to click through any of this
by hand. Separately, crit 9 (due **Mon 12 Oct, 13:30**, ~2 days out) requires
the app to be real-time — a change one person makes has to show up for
everyone else within about a second, no reload — plus one written-down
decision about concurrent use. None of the current code does that yet.

This plan builds all four together because they interact: once logging a
result requires picking a real member, a member who just joined has to show
up in other people's open forms *live*, or the membership gate itself becomes
the thing fighting the app's "logging should be effortless" goal
(`README.md`). That interaction is also where the crit-9 concurrency decision
comes from, rather than being bolted on separately.

Decisions already made with you: avatars are generated by default and
uploadable (like Reddit's default avatar + custom picture), group-vs-group
matches are a single final score per match (not per-player rows), and crit
9's real-time requirement is in scope here.

## Schema changes (`src/db.ts`)

- `members`: add `avatar_blob BLOB`, `avatar_mime TEXT`, `avatar_updated_at TEXT`
  (all nullable — `NULL` means "use the generated avatar"), via the same
  `ALTER TABLE ... ADD COLUMN` migration pattern already used for
  `password_hash`.
- `groups`: add the same three `avatar_*` columns, for the group's own
  profile picture.
- `results`: add nullable `winner_member_id`, `loser_member_id` (FK to
  `members`). Keep the existing `winner`/`loser` text columns (populated from
  the member's name at logging time) so old rows and existing display code
  keep working untouched; new rows get both.
- New table `group_matches`: `id`, `group_a_id`, `group_b_id`, `game`,
  `score_a`, `score_b`, `logged_by_member_id`, `created_at`. One row per
  inter-group match, visible on both groups' pages via
  `WHERE group_a_id = ? OR group_b_id = ?`.

## 1. Members must be real, and can't beat themselves

- `src/pages.ts`: replace the free-text `winner`/`loser` inputs in the log-a-result
  form with `<select>`s populated from `resultsForGroup`'s sibling,
  `membersForGroup(group.id)` (new query in `db.ts`), using member id as the
  option value.
- `src/server.ts` (`POST /g/:code/results`): resolve `winner`/`loser` as
  member ids, require both to belong to this group, and reject
  `winner === loser`. On failure, re-render the group page with an error
  (same pattern `authError` already uses) and don't insert a row.
- `src/db.ts` `addResult`: take member ids, look up names, store both id and
  name columns.
- **Existing test fix**: `spec/scorekeeping.test.ts` logs results against
  `"Sam"`, `"Ghost"`, `"Robin"` without registering them — once membership is
  enforced these would now be rejected. Register every named player before
  logging in that file (the stale-token case doesn't need a real `loser`,
  since it must fail before membership is even checked).

## 2. Avatars (members and groups)

- New `src/avatars.ts`:
  - `generatedAvatar(seed: string): string` — a deterministic SVG (initials +
    a color picked from a small fixed palette by hashing `seed`). No upload,
    no dependency, no storage.
  - Shared helpers for reading/validating an uploaded file: accept
    `image/png`, `image/jpeg`, `image/webp`; reject anything else or over
    300KB (no resizing library — keeps the no-native-deps approach
    `PROCESS.md` already committed to; a hard cap instead).
- Add `@fastify/multipart` (the only new dependency) and register it in
  `src/server.ts`.
- Routes, both following the same shape:
  - `GET /g/:code/members/:id/avatar` and `GET /g/:code/avatar` — serve the
    stored blob with its mime type if set, otherwise `generatedAvatar(...)`
    as `image/svg+xml`. `Cache-Control`/`ETag` from `avatar_updated_at`.
  - `POST /g/:code/members/:id/avatar` — only the signed-in member themself
    (`currentMember(req, group).id === id`); `POST /g/:code/avatar` — any
    signed-in member of the group (there's no group-admin concept, consistent
    with the existing trust model).
- `src/pages.ts`: show the avatar (`<img>` pointing at the routes above) next
  to each result row, on the sign-in/register card header, and in the group
  page header (the group's own "profile picture"), with a small upload
  control wherever a signed-in member can change one.

## 3. Group-vs-group matches

- `src/db.ts`: `addGroupMatch`, `groupMatchesForGroup(groupId)` (joins both
  group names/codes for display).
- `src/server.ts`: `POST /g/:code/matches` — signed-in member of this group
  enters an opponent group code + game + both scores; 404/error if the code
  doesn't resolve to a group.
- `src/pages.ts`: a "Group matches" section on the group page, separate from
  the intra-group results list, showing the opponent group's name + avatar +
  score, with the log-a-match form visible to signed-in members. Appears
  identically on both groups' pages since it's the same row.

## 4. Real-time (crit 9) + the concurrency decision

- New `src/live.ts`: a tiny in-memory pub-sub — `subscribe(code, fn)` /
  `broadcast(code, event)` — scoped per group code. In-memory is enough
  because `fly.toml` runs exactly one machine (`min_machines_running = 0`,
  no horizontal scaling), so there's only ever one process to broadcast
  from.
- `GET /g/:code/events` — an SSE endpoint (`reply.hijack()` + raw writes to
  `reply.raw`, no new dependency). On connect, subscribe; on `req.raw`
  `close`, unsubscribe.
- Broadcast points, each sending a re-rendered HTML fragment the client swaps
  in directly (reusing the same render functions as the full page, so there's
  one template, not two):
  - after `addResult` → a `result` event with the refreshed results list
  - after `addGroupMatch` → a `group-match` event with the refreshed group
    matches list
  - after `registerMember` → a `member` event with the refreshed `<option>`
    list for the winner/loser selects
- `src/pages.ts`: wrap the results list, group-matches list, and the two
  `<select>`s in elements with stable ids; a small inline `<script>` opens
  `new EventSource('/g/:code/events')` and replaces the matching element's
  `innerHTML` per event type.
- **The decision, written down** in `decisions/0001-live-update-scope.md`
  (ADR form, as the brief suggests): *new results, new group matches, and new
  member sign-ups push live to everyone with the group open; avatar changes
  do not* — a viewer sees a stale picture until their next reload. Options
  considered: push everything (rejected — image bytes are comparatively
  rare-churn and heavy for a 256MB machine to fan out); push only results,
  the minimum crit-9 asks for (rejected — once logging requires picking a
  real member, a person who just joined would be invisible in everyone
  else's open dropdown until they reload, which directly fights the
  "logging should be effortless" goal in `README.md`). Reconnecting (a
  closed tab, or the next day) just does a normal page load, which is
  already fully up to date from SQLite — no separate reconnect logic needed.

## 5. Seed script

- `scripts/seed.ts`, using the real `db.ts` functions (not raw SQL) so it
  exercises the actual code paths: creates 3 groups, 3–4 members each with
  known passwords, a handful of intra-group results, and 2 group-vs-group
  matches between the seeded groups. Skips groups that already exist by name
  instead of duplicating on a second run. Prints a summary (codes + logins)
  so you can click through by hand afterwards.
- `package.json`: `"seed": "DB_PATH=./data/dev.db node scripts/seed.ts"` —
  same `DB_PATH` convention as `dev`, so it never touches the production
  volume unless `DB_PATH` is explicitly overridden.

## 6. Spec tests ("test all the features too")

All run the existing way — real HTTP against the running app
(`spec/global-setup.ts`), asserting the contract, not the implementation:

- `spec/scorekeeping.test.ts`: fix the two now-invalid existing cases (above),
  add "logging a result naming someone who isn't a member is rejected" and
  "winner and loser can't be the same member."
- `spec/avatars.test.ts`: fresh member serves a generated (`image/svg+xml`)
  avatar; uploading a valid small PNG switches it to `image/png` with
  matching bytes; an oversized/invalid upload is rejected and the avatar is
  unchanged; same two cases for a group avatar.
- `spec/group-matches.test.ts`: a match between two seeded/created groups
  appears on both groups' pages with the right score; an unknown opponent
  code is rejected.
- `spec/live-updates.test.ts`: open the SSE stream for a group, log a result
  from a second request, assert the stream emits a matching event within a
  couple of seconds; same for a new member showing up in the stream.

## Verification

1. `pnpm typecheck`
2. Start the app (`pnpm dev` or equivalent) and run `pnpm seed`, then `pnpm check` —
   all spec files green, including the new ones.
3. By hand: open a seeded group's page in two browser windows, log a result
   in one, watch it appear in the other without reloading; try logging a
   result for a made-up name and confirm it's refused; upload an avatar and
   confirm it replaces the generated one; log a group-vs-group match and
   confirm it shows on both groups' pages.
4. `flyctl deploy --remote-only --ha=false -a comp4020-final-raazseven`, then
   repeat step 3 against the live URL (crit 9's bar is deployed, not just
   local).
5. Commit incrementally through the phases above (schema → avatars → group
   matches → real-time/ADR → seed/tests), not as one giant commit — that
   commit history is the process evidence `PROCESS.md` and
   `reflections/crit-9.md` cite.
